# 通用时序知识图谱 V4

本文是 [项目契约](PROJECT_CONTRACT.md) 下的知识领域设计。它定义图谱如何表达和维护知识，不改变 OpenClaw 唯一主控和 Workboard 唯一任务状态源。

实现验收状态见 2026-10-22 知识底座实测：来源复核、时间/作用域和多写入入口仍有已复现缺口。本文的设计要求不能替代实现通过证明。

后续修复记录见首批实现验证。本轮核心与插件写入已统一；可信值由有效评估与同一时点的冲突派生；查询使用 `[valid_from, valid_to)`，非法时间不作为有效现状。事实已标 superseded 但缺少结束时间时不冒充现行事实。

声明身份与时间实例分开：A -> B -> A 的最后一个 A 必须带新的明确生效时间，生成独立事实 ID；旧来源重放保留旧事实归属。不同作用域不互相取代。维护请求取代失败时保存候选和原因，复核回执转 needs_input，正确重试可完成；任务重新判断和真实模型闭环仍需独立验收。

## 设计结论

Shadow Agent 只维护一套通用知识底座，不分别开发软件版本、日报、会议或人员管理图谱。

软件版本管理只是图谱能够回答的一类问题。新增领域时可以增加词汇和事实，不增加专用数据库、状态机或传播代码。

底层遵循六项原则：

1. 原始证据按保留策略独立保存，摘要和图谱不能替代原文。
2. 实体类型和关系采用开放世界模型，未命中词表也允许入图。
3. 每条事实必须回到原始证据或可展开的推理链。
4. 现实有效时间与系统获知时间分开保存。
5. 证据等级只是摘要，方法、环境、范围和结果必须单独保存。
6. 传播规则只发现风险，不自动宣布影响已经发生。
7. 图谱优先保存稳定事实和认知路标，不复制所有消息、日志和工具结果。

## 分层结构

### 来源导航与语义知识分离

仓库快照/历史线索和项目文档目录不由最后一条 Evidence 覆盖同一个摘要。按 [ADR-0044](decisions/0044-derived-knowledge-entry-maintenance.md)，程序维护有界 `knowledgeEntry` 派生表示与 `retrieval_source` 精确引用；人工/模型简介保持既有高优先级。文档目录所选资料逐文件建立 Document 入口，不把原文摘要当成已验证事实。历史修复和后续增量必须走同一个维护函数，不能仅手工改展示文本。

### 原始证据层

保存 Codex 会话、Git 记录、文档、飞书消息、测试输出、人工输入等原始材料。

原始证据是不可替代的来源。工具输出和过程痕迹即使不进入长期语义图，也保留用于核验。

普通飞书消息、构建日志和工具输出默认到此层为止，并进入全文索引。只有它们形成稳定身份、长期事实、决定或“以后去哪查/问谁”的路标时，才提升到语义图层。

### 知识单元层

每个值得长期召回的证据单元生成一张知识召回卡：

| 字段 | 用途 |
|---|---|
| title | 人可读名称 |
| summary | 不替代原文的短摘要 |
| keywords | 关键词、缩写、同义词、标识符 |
| retrieval_cues | 这条知识可以回答的自然语言问题 |
| scope | 适用项目、版本、设备、人员、时间或环境 |
| salience | 长期使用价值和处理优先级 |
| content_hash | 判断是否需要重新处理 |
| evidence_id | 回到原始证据 |

自动采集和人工新增知识都走这一步。关键词只负责召回候选，不能决定最终事实。

### 语义图层

采用与 W3C PROV 相近的三个顶层概念：

| 顶层类型 | 定义 | 示例 |
|---|---|---|
| Entity | 具有相对稳定身份的物理、数字或概念对象 | 文档、源码修订、软件版本、接口契约 |
| Activity | 在一段时间内使用、改变或生成实体的活动 | 会话、会议、构建、测试、审批、部署 |
| Agent | 对活动或实体承担责任的主体 | 用户、Codex、OpenClaw、组织、外部系统 |

领域类型只是开放子类型。未知类型自动登记为 learned 类型，后续可补父类型；未知关系自动登记但默认不传播影响。

Fact 保存主体、关系、客体、现实有效区间、观察时间、置信度和认知状态。Fact 至少关联一项：

- Evidence assessment：证据支持、反驳或仅提及该事实。
- Derivation：Codex 根据哪些已有事实推导出该候选关系。

### 任务层

Workboard 继续维护待办、进行中、阻塞、完成等执行状态。知识图谱可以描述任务与文档、版本、人员和决定的关系，但不成为第二个任务主控。

### 工作焦点投影

在知识图谱和 Workboard 之上维护一份可重建的长期工作简况：工作职责、活跃工作流、近期目标、风险和等待项。它不保存任务状态，只给主动巡检提供稳定背景。简况缺失时必须建立；之后仅把相关变化作为复核候选，普通日志和批次入库不触发整份重写。

每轮巡检读取这份简况、Workboard 活跃卡片和新增变化，按以下次序选择注意力：

1. 已逾期或临近明确截止时间。
2. 用户人工置顶。
3. 阻塞后续任务或影响多人交付。
4. 高风险、高业务影响或高优先级。
5. 与长期职责和近期目标相关的新变化。
6. 旧知识语义精炼，仅在没有更重要工作时运行。

截止时间必须来自人工输入、任务字段、文档明确日期或规范标签。计划启动时间不等于截止时间；缺少来源时保持未知。

### 工作记忆与预期记忆

知识图谱不承担全部记忆职责：

- OpenClaw 稳定会话保存当前目标、最近讨论和未决问题。
- Workboard 保存要做什么和任务状态。
- condition watch 与 reminder 保存等待和未来提醒。
- 图谱保存跨会话仍有价值的事实与认知路标。

因此“不知道答案”不要求先把所有历史写进图谱。Agent 只需知道原文、代码、系统或人员入口，再按需重新取得。

## 认知路由

认知路由使用同一套 Entity 和 Fact，不建立专用联系人数据库。常见实体为 `KnowledgeTopic`、`InformationSource`、`CodeLocation`、`CommunicationChannel`、`Person`、`Team`、`Role`、`Procedure`、`Skill`；常见关系为 `DOCUMENTED_IN`、`IMPLEMENTED_IN`、`QUERY_VIA`、`DISCUSSED_IN`、`RESPONSIBLE_FOR`、`EXPERT_IN`、`CONTACT_VIA`、`CAN_ANSWER` 和 `FALLBACK_TO`。

`shadow_context_resolve` 按以下顺序生成解题计划：

1. 返回已有证据支持的知识卡和事实。
2. 返回文档、代码、仓库、会话、系统或步骤入口。
3. 返回能回答该主题的责任人、专家和联系渠道。
4. 仍不足时返回已尝试路径、缺失信息和最小下一步。

外部联系只生成草稿。获得发送授权后才调用飞书工具，并创建回复 condition watch；询问发送成功不等于问题解决。

## 开放世界与模型补链

图谱词汇的作用类似 MCP 工具和 Skill 描述：提供名称、用途、别名、触发场景和关系语义，帮助模型找到候选项；它不是封闭枚举。

实际流程为：

1. 用关键词、别名、全文和知识召回卡找出候选实体与证据。
2. Codex 阅读候选对象、邻居、时间和来源证据。
3. Codex 判断是否为同一实体、已有关系或新的候选关系。
4. 有已有词汇时复用稳定关系；没有时创建 learned 关系。
5. 新关系先以 proposed 保存，并注明证据或推理来源。
6. 后续证据可以支持、反驳、修订、合并或取代它。

因此“时间戳传递”“timestamp propagation”“时间字段透传”不要求字符串相等。词语只负责召回，模型结合上下文确定是否关联。

## 人工与自动知识录入

无论来源是自动采集、你在对话中明确补充、粘贴的笔记、已读取文件，还是 Codex 已查看的链接正文，都采用同一条链路：

1. 原文以不可变 Evidence 保存，并记录来源类型、定位、时间和可选作用域。
2. 同一次处理必须生成 `summary`、至少三个 `keywords` 和至少两个 `retrieval_cues`。
3. 关键词包含业务词、同义词、缩写、稳定标识符和必要的旧称；不能只机械截取高频词。
4. `retrieval_cues` 用自然问题描述它能回答什么，例如“这个提交属于哪个任务”“该决定适用于哪个版本”。
5. Codex 再判断需要保留的实体和关系，并用该 Evidence 支持候选事实。
6. 任务、人工确认完成和下一步仍写入 Workboard；其中有长期复用价值的决定或事实，才额外进入知识图谱。

`shadow_context_capture` 是人工入口。对文件和链接，先由有权限的工具读取内容，再把正文摘要、来源定位和召回信息传入；该工具不绕过权限直接抓取文件或网页。

`shadow_context_revise` 是纠错入口。它追加新的纠正 Evidence、建立 `supersedes`、失效旧召回卡，并把失去全部有效支持的事实和派生事实降为待复核。仍有独立、未过期支持的事实保持有效。查询只把未过期、非争议、非反驳且具有当前支持的事实放入 `verifiedFacts`；其他材料分别进入 `reviewPending` 或 `conflicts`。

## 软件版本的准确定义

软件版本不是版本名称、Git 分支、单个提交、一次构建或一次部署。

可复现的软件版本身份定义为：

```text
SoftwareVersionIdentity = ProductIdentity + VersionManifestHash

VersionManifest =
  SourceRevisionSet
  + DependencyLock
  + BuildProfileAndToolchain
  + InterfaceAndSchemaRevisions
  + ConfigurationBaseline
  + ProducedArtifactHashes
```

对于多个并列仓库组成的 ExampleVision 软件，版本清单必须指出每个仓库的不可变源码修订。只写 `develop` 或 `v5.0.0` 不能唯一复现版本。

| 类型 | 准确定义 | 不是 |
|---|---|---|
| SoftwareProduct | 跨版本保持身份连续的产品 | 某个二进制文件 |
| SoftwareVersion | 由不可变版本清单确定的产品状态 | 标签文字或分支名 |
| VersionManifest | 版本完整组成及内容哈希 | 普通发布说明 |
| SourceRevision | 提交哈希标识的不可变源码状态 | 可移动分支 |
| MutableReference | 分支等可移动引用 | 稳定版本身份 |
| ChangeSet | 从已知状态产生新状态的变更活动 | 变更后的版本本身 |
| BuildExecution | 在确定工具链和配置下进行构建的活动 | 软件版本 |
| BuildArtifact | 构建产生且有内容哈希的二进制或软件包 | 源码修订 |
| InterfaceContract | API、ABI、协议、数据结构、配置或持久化格式约定 | 任意内部实现细节 |
| TestExecution | 某测试在确定版本和环境上的一次执行 | 永久有效的质量结论 |
| Deployment | 把确定产物放入目标环境的活动 | 新版本身份 |

这些仍然只是通用 Entity、Activity 和 Fact 的实例，没有专用版本表。

## 证据等级

| 等级 | 名称 | 最低含义 | 典型证据 |
|---|---|---|---|
| E0 | 推测 | 没有直接来源 | 模型推断、待验证关系 |
| E1 | 陈述 | 有人员或二手材料陈述，未核对原始对象 | 口头说明、摘要、转述 |
| E2 | 实物证据 | 直接检查原始信息对象 | Git diff、源码、文档、消息、结构化记录、静态分析 |
| E3 | 受控执行 | 在本地或仿真环境可重复执行 | 构建、单元测试、模拟、受控实验 |
| E4 | 集成验证 | 在目标集成环境或端到端链路执行 | 硬件在环、系统测试、目标环境联调 |
| E5 | 现场确认 | 在真实现场或生产环境观察并在明确范围内验收 | 现场设备验证、生产观测、责任人验收 |

证据等级不能脱离证据画像单独使用：

- 等级不等于置信度。E2 可以高置信证明“头文件未变”，不能证明“现场绝无影响”。
- 一次测试只验证指定提交、配置、设备和测试用例。
- 构建通过是 E3，不自动升级为真实设备或现场验证。
- 普通人工陈述通常是 E1；只有明确对象、环境和验收范围的现场确认才是 E5。
- 新信息不会仅因时间较新就静默覆盖旧事实；矛盾进入冲突记录。

## 影响传播

关系类型保存两个独立方向的建议权重：

- `forward_impact_weight`：主体变化是否可能影响客体。
- `reverse_impact_weight`：客体变化是否可能影响主体。

例如 `Consumer DEPENDS_ON Contract`：Contract 改变可能影响 Consumer，因此反向权重较高；Consumer 改变通常不影响 Contract，正向权重为零或很低。

传播过程：

1. 从已知发生变化的实体开始。
2. 只遍历当前有效且未被反驳的事实。
3. 按关系方向、关系权重、事实置信度和证据等级逐跳衰减。
4. 无确定传播语义的关系不丢弃，而是作为 `unmodeledEdges` 返回给 Codex。
5. 输出可能受影响对象、完整路径、每跳证据等级和路径置信度。
6. Codex结合原始证据判断是否建立候选事实、安排验证或创建任务。

传播结果不能直接写成“已影响”。只有新的测试、观察或确认才能形成已验证的影响事实。

### 关系链维护

图谱不会因为新材料到达就删除旧结论，而是沿证据和推理链维护认知状态：

1. 一条事实的全部支持证据都被新证据 `supersedes` 后，该事实可信状态降为 `proposed`，复核原因写入 `graphMaintenance.state=needs_review`。
2. 只要仍有一项未被取代的支持证据，事实保持当前状态。
3. 依赖该事实的派生结论递归降为 `proposed`，并记录失效输入和传播深度。
4. 补入新的有效支持证据后，E2 及以上恢复为 `supported`，较弱证据恢复为 `proposed`。
5. `refuted`、`disputed` 由当前反驳评价和开放冲突推导，不接受入口任意写死；证据变化后统一重算。
6. 每次实际状态迁移写入审计历史；无变化的定时检查不写空审计记录。

这套维护逻辑只依赖通用 Evidence、Fact 和 Derivation，不为软件版本或其他领域写专用传播代码。

## `c67c789` 示例

该相机提交可以表达为：

```text
SourceRevision(c67c789)
  GENERATED_BY -> ChangeSet(相机日志与显式 emit 改动)

ChangeSet
  PART_OF -> Session(019fab71...)
  MODIFIES -> SourceFile(AT_Camera.cpp)

MergeRequest(AT_Camera !23)
  REFERENCES -> SourceRevision(c67c789)

Claim(未修改外部接口)
  supported_by -> Git diff evidence, E2/source_inspection
```

Git diff 能直接证明头文件、信号签名、数据结构和协议未变，因此“接口契约未变”在该提交范围内可获得 E2 支持。每 500 帧新增日志属于另一条运行行为事实，不能被“接口未变”掩盖。

后续构建记录可以增加 E3，目标链路或真实设备测试可以分别增加 E4/E5；证据并存，不压缩成模糊的“已验证”。

## 统一人工反馈 Episode

用户在宠物中的明确记忆、任务下一步、任务完成确认、飞书消息修改批准和带原因拒绝，不建立领域专用学习系统，而是统一追加为现有 Evidence 和知识召回卡。`humanFeedback` 元数据只描述动作、对象、来源和作用域提示；修改前后文本、拒绝原因和有界上下文保存在经过脱敏的 Evidence 正文中。

语义复核继续使用开放 Entity 和 Fact：可根据证据建立 `Responsibility`、`Preference`、`Procedure` 或 learned 类型，并以项目、人员、渠道、会话、任务类型等实体表达作用域。单次操作首先是对该对象有效的人工证据；只有用户明确表达长期规则，或后续独立证据持续支持时，才提升为更广范围的职责或偏好。无长期价值时记录 `no_durable_facts`，不为了“自学习”强行造关系。

业务动作和知识投影分开：Workboard、出站草稿和提醒仍保存各自状态；知识图谱只保存用户表达、理由、修改和可复用含义。后续纠正使用原有不可变 Evidence、认知状态、冲突、修订和取代链，不覆盖历史。

`completeKnowledgeAnnotation` 对具有明确任务绑定的人工反馈，在保存复核/队列结果的同一事务写入 `task_progress_due(reason=knowledge_feedback_reviewed)`。事件携带原 Evidence ID、发生时间、复核结果和事实 ID；注意力包保留有界的结果/理由，不复制任务历史，不授予新权限。以证据内容指纹、原任务、复核状态/结果和排序后的事实 ID 比较同任务、同证据的最近一次通知；连续同结论重试复用原事件，不比较处理时间或摘要/理由措辞。经过其他结论后重新进入原结论（A -> B -> A）必须形成新事件，不能用永久状态哈希去重漏掉歧义解除。通知摘要是当时快照，最新复核详情按 Evidence ID 读取。

一次性反馈即使不进入长期图谱也要通知原任务；`needs_input` 只通知主控判断是否真的需要人，不直接给用户新增待办。被新证据取代的旧反馈不得重新完成标注；修订时原子退休它未消费的任务通知。新证据沿既有 `supersedes` 链追溯显式人工反馈关联的原任务，多个明确任务分别通知；不复制旧反馈的 `explicitUserInput` 或授权。结果差量不回送原任务，避免主控结果与知识维护互相触发。无绑定资料不按项目/姓名扩散，其他关联任务仍通过既有证据/条件链由主控判断。

## 旧知识升级

旧库不把所有原始消息和工具痕迹逐条交给模型。迁移过程为：

1. 从会话摘要、Git 摘要、长期文档和人工导入材料建立待升级队列；普通飞书消息只留在 Evidence Log，不逐条建卡。
2. 立即生成带内容指纹的临时召回卡，使旧知识先可被检索。
3. 人工反馈、显式导入和当前外部任务进入 `active_review`，由触发它们的稳定会话按 Evidence ID 精确领取；不得等待 FIFO 空闲巡检。
4. 已有临时召回卡的旧会话、Git、仓库和文档摘要进入 `cold_inventory`。它们保持可检索，只有检索命中、人工指定或活动任务引用时才晋升，不按年龄批量调用模型。
5. Codex 只把长期有价值且有证据的实体和关系补入语义图。
6. 每个精炼单元必须显式记录语义复核状态：`pending`、`completed` 或 `needs_input`；`completed` 还必须记录 `facts_recorded` 或 `no_durable_facts`。仅写完摘要不算升级完成，`facts_recorded` 也不代表事实可信。
7. 完成后记录 extractor version 和 content hash；内容不变就永不重复处理。
8. 新证据或内容变更才重新进入活动队列。
9. Codex 整理后的名称和摘要具有更高展示优先级；后续自动采集只更新时间、状态和来源，不把它覆盖回原始长标题。
10. 目录、项目、仓库和会话映射属于 `structural_route`。它们保留确定性来源并帮助导航，但不进入 `verifiedFacts`、待复核知识或职责判断。

写入、查询和认知路由统一读取 `review_status/review_outcome` 规范列，不再按 metadata 中的旧 `graphReview.status` 双读。`completed + no_durable_facts` 仍保留可回源入口；`completed + facts_recorded` 不能将 proposed/disputed/refuted 事实升级为可信。只有 supported、当前支持证据有效且满足复核条件的事实进入 verified 分类。被取代的召回卡不再作为当前入口。认知路由返回的是有界候选而非穷尽结果；预算裁剪须保留 `truncated` 和遗漏数量，不能让模型把截断误读为没有知识。

`npm run audit:knowledge` 用于只读检查活动复核、冷库存、召回卡质量、结构路由来源、证据链和 learned 关系传播权重；`npm run audit:knowledge:strict` 只把活动债务和治理异常作为失败。冷库存单独报告，不得为了让数字归零而删除或批量总结。

这样可以逐步覆盖旧知识，又不会每十五分钟重扫几十万条历史。

## 通用工具

| 工具 | 作用 |
|---|---|
| `shadow_context_status` | 查询图谱、变化队列、知识升级和采集服务健康度 |
| `shadow_context_focus` | 返回长期工作简况和按 DDL、影响与职责排序的工作雷达 |
| `shadow_context_focus_update` | 选择现有本人事实的展示类别并更新任务关注覆盖层；不独立写简况正文或可信状态 |
| `shadow_context_changes` | 以租约领取有限的新变化及局部图上下文 |
| `shadow_context_ack` | 确认变化已处理、忽略或因瞬时失败暂缓 |
| `shadow_context_resolve` | 返回已知事实、查询入口、可询问对象、授权门和非阻塞后续方案 |
| `shadow_context_query` | 查询知识单元、实体、事实、已关联证据和推理链；原始全文按认知路标到具体来源检索 |
| `shadow_context_entity` | 展开一个实体的邻域与来源 |
| `shadow_context_vocabulary` | 按名称、别名和描述查询开放词汇 |
| `shadow_context_capture` | 通过统一知识 Episode 入口追加人工知识证据和召回卡；宠物反馈复用同一后端 |
| `shadow_context_revise` | 追加纠正证据、取代旧卡并传播失效状态 |
| `shadow_context_enrichment` | 小批量领取需要升级的旧知识和新知识 |
| `shadow_context_annotate` | 写入摘要、关键词、可回答问题和范围 |
| `shadow_context_propose` | 追加有证据或推理链的候选关系 |
| `shadow_context_impact` | 返回建议性影响路径和未建模关系 |

## 明确不做

- 不为每个业务领域创建新数据库或专用图引擎。
- 不要求所有知识都必须关联项目。
- 不用单一分数替代证据方法、环境和范围。
- 不让规则未命中等于知识不存在。
- 不把模型推断伪装成已验证事实。
- 不让知识图谱成为第二个任务主控。
- 不为每条消息创建图节点或语义摘要任务。
