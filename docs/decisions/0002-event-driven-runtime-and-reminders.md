# ADR-0002 实时触发、连续会话、条件跟踪与提醒

- 状态：接受
- 日期：2026-08-12
- 决策者：用户、Codex
- 关联契约：INV-01、INV-02、INV-13 至 INV-18

## 背景

只依赖 15 分钟 Heartbeat 无法及时处理飞书新消息、提及、审批、任务变化和连续对话，也不能提供可靠的到期提醒。后续实测还表明，空闲 Heartbeat 与逐消息唤醒会反复发送巨大固定上下文。新增实时代码不能演变为第二个 Agent 主控或第二套任务状态。

## 决定

在上下文服务进程中增加确定性的事件接入层和注意力调度器。个人消息、文档、任务和审批由 `user` 身份 API 构成主数据链；任务和审批事件提供实时加速。飞书机器人消息是独立的 `bot` 对话入口。所有入口只保存证据、去重并按会话/来源合并；只有存在实质变化时才唤醒唯一 OpenClaw 主控。

周期 Heartbeat 默认关闭。注意力队列持久保存到本机数据库设置，普通群聊、机器人消息、直接消息使用不同冷却时间，并设最大等待和失败退避。归属标签只调整时效，最终任务归属由主控结合完整会话、职责和现有任务判断。文档目录与正文变化分开，Base 容器编辑时间不再直接触发语义处理。

后台事件订阅未批准时属于“实时能力缺口”，不得作为整体故障自动重连，也不得阻塞用户身份 API 的有界轮询和 15 分钟补偿。

直接发送给机器人的单聊和群聊提及可由 OpenClaw 在原会话回复。个人账号消息只生成证据和唤醒，未经授权不代用户回复。OpenClaw 继续使用 Workboard 维护任务；对话本身不是任务。

提醒意图先写入 Shadow Context 数据库和可靠出站队列，后台再创建 OpenClaw Cron。到期不改变任务状态，人工确认和稍后提醒均产生审计状态。

等待外部回复、任务状态或文档结果时，创建带证据游标的 `condition_watches`。实时事件和增量采集负责立即检查，30 秒检查只负责兜底；筛选命中只形成候选，OpenClaw 在原稳定会话中作语义确认。个人飞书会话也按聊天或话题绑定稳定会话，但保持只读，未经授权不代用户回复。

## 备选方案

- 仅缩短 Heartbeat：会增加无变化巡查成本，仍不能稳定维护连续会话。
- 仅延长轮询：降低频率但不解决错误变化、重复上下文和逐消息判断。
- 新建独立实时 Agent：会违反唯一主控和唯一任务源。
- 把提醒当 Workboard 任务：会混淆“要做什么”和“何时通知”。
- 只依赖内存定时器：重启和崩溃后会丢提醒。

## 影响

数据库新增事件回执、会话映射、提醒投影、条件跟踪和可靠出站队列。上下文服务需要监督多个 lark-cli 子进程、处理断线重连、增量条件检查和出站重试。宠物新增提醒视图和确认操作。

## 数据迁移

新增表均为幂等建表，不重新解释旧证据或 Workboard 卡片。旧任务、巡查和知识候选表保持兼容历史，不参与新链路。

## 回退方案

关闭 `feishu.realtime.enabled` 和快速轮询后，本地证据增量与 24 小时全面核对仍可运行，但飞书时效下降。需要临时恢复周期巡检时可显式开启低频 Heartbeat；已有事件回执、注意力状态和提醒投影保留。

## 验证

- 数据库模式和幂等事件单元测试。
- 模拟事件重复、断线重连、同会话串行处理和群聊提及过滤。
- OpenClaw 会话与 Cron CLI 集成测试。
- 宠物提醒显示、确认和稍后提醒 E2E。
