# 长期委托与主动推进

目标是减少用户真实工作，不是制造更多任务、通知或模型调用。长期研究、普通交付、缺失工具的构建都使用已有 Workboard 卡片。不能因发现相关信息就接管他人的工作。

## 每次推进

1. 读当前卡片及 `shadow_context_focus(taskId)` 的方案、版本和最近结果。先处理新的人工指令及责任变化，再考虑旧计划。必要证据按位置检索，不载入所有历史。
2. 明确这一轮怎样推动验收：直接交付、验证假设、解除阻塞、制作缺少的工具，或询问有能力回答的人。不要把“再看一下”当行动，不要凭频繁复查刷进度。
3. 结合用户优先级、明确截止时间、近期输入、依赖及预期减少的人工工作，解释为何现在做这一步。没有新外部消息也可执行已授权的内部实验。
4. 使用现有子任务、HITL、条件跟踪和检查点。每轮留下一个可观察续接点；时间由主控根据事件条件决定。技术兜底时间不代表业务计划。
5. 接收结果，按验收接受、调整方案、请求具体条件或停止。不能无条件重试相同失败步骤；不自动把现实验证当已完成。

## 持久行动方案

每次检查点先读取精确 `shadow_context_focus({taskId})`，将返回的 `checkpointRevision`、`bindingRevision`、`execution` 分别传为顶层 `expectedCheckpointRevision`、`expectedBindingRevision`、`expectedExecution`。实际调用方由 runtime 工厂确认；不能伪造其他卡的 `ownerSessionKey`。这些版本与下面的 `progressPlan.expectedRevision` 不同，即使本轮不修改方案也要传。

`applied=false` 表示旧结果仅保留为证据/学习，不是已更新进展，不允许据此 ACK 当前事件。重读 focus，根据最新结果重新决策。终态可以留证据，但不追加活动 continuation。完全相同的重试使用相同 `idempotencyKey`；不同内容不能复用。

通过 `shadow_task_checkpoint.progressPlan` 写入：

- `expectedRevision`：刚读取的方案版本，首次为 0；冲突后重读，不能覆盖更新。
- `outcome` / `successCriteria`：当前卡片目标和验收的简明解释，不是第二份任务权威。
- `authorizedScope`：已有授权范围，不是新增权限。
- `approach`：当前解法/研究假设与关键未知项。
- `nextAction`：下一个有界可执行动作。
- `stopCondition`：何时完成、停止当前路线或请求用户决定。
- `whyNow`：现在执行的价值、时机或新证据。

验收范围以用户明确目标、已有卡片及原始约定为准。模型建议的额外工作、交付物的后续用途或下游验证，不自动成为本卡的强制完成条件；需要扩展时明确标为建议或待确认。缺失信息先判断是否真正阻塞当前动作，不把所有可澄清项都变成人工前置条件。

每项最多 600 字符，总计不超过 6 KiB。方案有变化才修订；其他检查点保留已有方案。下一次注意力包只携带当前卡片的简版，完整内容按 taskId 读取。方案与检查点同一事务保存，但 Workboard 仍是唯一任务状态源。

## 结果回到记忆

有可复用且有原始证据的结论时，在同一检查点中提供 `learning.durableCandidates`、至少三个 `keywords` 和两个 `retrievalCues`，可附 `decisions`、`unknowns`，并给出 `evidenceIds`。关键词和检索问题由语义归纳，不能机械填模板词。后端原子保存结果、方案和知识差量；失败则整体回滚；同一结果重试不会再建差量。

这只加入现有知识维护队列，不直接把结论变成可信事实。专用维护会话比较已有知识、支持/反对证据、范围和冲突后处理。不要再为同一结果调用一次 delta capture。临时输出无需学习；人工纠正仍走既有人工知识 episode，不增加平行记忆体系。
